# Contributing to sping

Thanks for your interest in contributing to sping!

We welcome bug reports, feedback, documentation improvements, and feature ideas. Our goal is to keep sping focused, reliable, and maintainable across Linux, macOS, and Windows.

## How changes reach sping

GitHub hosts sping's public releases; development happens in a separate repository. Pull requests are reviewed here, but they are not merged as they are: an accepted change is applied upstream and ships with the next release, and the CHANGELOG credits its author.

## Before contributing

**Bug fixes and small documentation changes** are welcome as focused pull requests.

**New features, significant changes to existing behavior, or modifications to the probing and rendering architecture** should be discussed in an issue before implementation.

Please describe the problem you're trying to solve, your proposed approach, and any alternatives you've considered.

An open issue or a positive response to an idea does not imply that the feature has been approved or scheduled. Please wait for maintainer agreement on scope before investing substantial implementation effort.

## Reporting a bug

Please include:

- the output of `sping --version`;
- your operating system and, for display problems, your terminal;
- the command you ran, what you expected, and what happened;
- the output with `--debug`, if it shows something relevant.

Please report security issues privately, as [SECURITY.md](SECURITY.md) explains, not in a public issue.

## Pull requests

- Keep each PR focused on one well-defined change.
- Avoid unrelated refactoring or introducing additional features.
- Preserve existing CLI behavior and documented interfaces unless a change has been explicitly agreed upon.
- The JSON output follows a stable contract ([JSON_CONTRACT.md](JSON_CONTRACT.md)): new fields may be added, but existing fields keep their types and meaning.
- Include appropriate tests for new behavior and bug fixes.
- Preserve regression-test coverage. Update golden tests to validate the intended complete output rather than truncating or masking differences.
- Document user-visible changes where appropriate.
- Consider portability across Linux, macOS, Windows, and supported CPU architectures.

## Development checks

sping needs Rust **1.88** or newer. Before submitting a PR, run the checks CI runs:

```sh
cargo fmt --check
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked
cargo build --release --locked
```

If you change platform-specific code, also check that it compiles for the other platforms:

```sh
rustup target add x86_64-apple-darwin x86_64-pc-windows-gnu
cargo clippy --locked --target x86_64-apple-darwin --all-targets -- -D warnings
cargo clippy --locked --target x86_64-pc-windows-gnu --all-targets -- -D warnings
```

Some platform-specific behaviors may require additional testing: say in the PR what you tested, and on which systems.

## AI-assisted contributions

AI-assisted development is welcome, but contributors are responsible for understanding, reviewing, testing, and maintaining the code they submit.

AI-generated code is subject to the same quality, correctness, and review requirements as any other contribution. If a substantial part of a contribution was generated by an AI tool, please say so in the PR description.

## Review and acceptance

All contributions are reviewed for correctness, maintainability, compatibility, test coverage, and alignment with the project's goals.

Maintainers may request changes, defer proposals, or decline contributions that do not fit the project's direction.

A pull request is not a guarantee of acceptance.
